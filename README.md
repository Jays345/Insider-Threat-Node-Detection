# Insider Threat Detection System

A Python-based insider threat detection prototype that analyzes user activity logs, identifies potentially unusual behavior, assigns risk scores, and presents findings through a Security Operations Center (SOC) dashboard.

The project combines supervised and unsupervised machine-learning techniques with user-behavior features to help security analysts investigate suspicious activity.

> **Project status:** Prototype for learning, experimentation, and demonstration. The included activity generator creates synthetic data; results should not be interpreted as validated performance on real enterprise environments.

## Features

- **Synthetic activity generation:** Creates up to 6,000 activity-log records across existing database users, covering a rolling 30-day period.
- **Behavioral feature engineering:** Uses file access, sensitive-file access, failed logins, USB activity, login time, weekend activity, user baselines, rolling averages, and changes in behavior.
- **Hybrid anomaly detection:** Combines XGBoost, an autoencoder, Isolation Forest, and Local Outlier Factor (LOF) into a risk-scoring pipeline.
- **Risk categorization:** Assigns `Normal`, `Review`, or `Critical` labels based on the configured risk-score thresholds.
- **Threat explanations:** Adds human-readable reasons such as after-hours login, unusual file access, sensitive-data spikes, and multiple failed logins.
- **Model evaluation:** Produces classification reports, confusion matrices, ROC and precision-recall curves, and model comparisons.
- **FastAPI backend:** Exposes authenticated endpoints for risk records, critical threats, alerts, and user investigation data.
- **Streamlit SOC dashboard:** Displays overall metrics, model-score comparisons, risk distribution, top-risk users, critical threats, and user-level investigations.

## How it works

1. **Prepare the database.** MySQL stores user records, activity logs, generated risk scores, and alert data.
2. **Generate activity logs.** `simulate_activity.py` creates synthetic behavior records for users already present in the `users` table.
3. **Engineer behavioral features.** `feature_engineering.py` calculates user-level baselines, deviations, z-scores, rolling averages, and after-hours indicators.
4. **Detect anomalies.** `anomaly_detection.py` loads `activity_logs`, trains and evaluates its models, calculates a hybrid risk score, assigns risk levels, and writes results to `risk_scores`.
5. **Inspect results.** `evaluation_and_visualization.py` visualizes risk patterns and evaluates predictions against the `is_anomalous` labels in the dataset.
6. **Explore through the API and dashboard.** FastAPI serves risk and investigation data; Streamlit calls the API to render the SOC dashboard.

## Requirements

A schema or migration file was not included in the supplied scripts, so create or import a compatible schema before running the pipeline.

## Installation

### 1. Clone the repository

```bash
git clone https://github.com/YOUR-USERNAME/YOUR-REPOSITORY.git
cd YOUR-REPOSITORY
```

Replace the URL and repository name with your own GitHub repository details.

### 2. Create and activate a virtual environment

**Windows (PowerShell):**

```powershell
py -m venv .venv
.venv\Scripts\Activate.ps1
```

**macOS / Linux:**

```bash
python3 -m venv .venv
source .venv/bin/activate
```

### 3. Install dependencies

```bash
python -m pip install --upgrade pip
pip install pandas numpy mysql-connector-python scikit-learn tensorflow xgboost sqlalchemy joblib fastapi "uvicorn[standard]" streamlit requests plotly matplotlib seaborn PyJWT python-dotenv
```

TensorFlow compatibility can depend on your Python version and operating system. If installation fails, use a Python version supported by the TensorFlow release available for your platform.

### 4. Configure environment variables

Create a local `.env` file in the project root. Do **not** commit it to GitHub.

```dotenv
DB_HOST=localhost
DB_PORT=3306
DB_USER=your_mysql_username
DB_PASSWORD=your_mysql_password
DB_NAME=insider_threat_db
SECRET_KEY=replace_with_a_long_random_secret
```

`db.py` reads the MySQL values from these variables. `api.py` uses `SECRET_KEY` to sign JWT tokens.

You can create a committed `.env.example` containing placeholders only:

```dotenv
DB_HOST=localhost
DB_PORT=3306
DB_USER=your_mysql_username
DB_PASSWORD=your_mysql_password
DB_NAME=insider_threat_db
SECRET_KEY=replace_with_a_long_random_secret
```

Generate a strong secret key for your local environment. Never publish real credentials, tokens, or production secrets.

### 5. Prepare the MySQL database

Create the database and import or create the required tables before running any scripts. At minimum, review the SQL statements in the project to ensure that your schema contains the columns they use.

The scripts refer to these tables:

- `users`
- `activity_logs`
- `risk_scores`
- `alerts`
- `file_access_logs`
- `login_logs`

`simulate_activity.py` requires users to exist in `users` and expects `user_id` and `department`. The detection pipeline reads `activity_logs` and writes calculated records into `risk_scores`. The API and dashboard also expect the supporting tables and columns used in their queries.

> A database schema is not included in the supplied project files. The table names above are not a complete schema definition; check each SQL query before creating your tables.

## Running the project

Run commands from the directory layout expected by the scripts. Several scripts use relative paths such as `../dataset/`, so your working directory and folder structure matter. Create the expected output directories before running scripts.

### 1. Generate synthetic activity

```bash
python simulate_activity.py
```

The generator attempts to insert 6,000 records into `activity_logs`. Run it only when you intend to add a new synthetic dataset.

### 2. Generate behavioral features (optional analysis stage)

```bash
python feature_engineering.py
```

This writes `../dataset/advanced_insider_dataset.csv` relative to the current working directory. Adjust the output path or working directory if needed.

### 3. Run anomaly detection

```bash
python anomaly_detection.py
```

This trains the configured models, calculates risk scores, writes results to `risk_scores`, and exports `../dataset/insider_activity_with_anomalies.csv`. Training includes randomized hyperparameter search for XGBoost and may take some time.

### 4. Start the API

In a terminal, run:

```bash
uvicorn api:app --reload --host 127.0.0.1 --port 8000
```

Open the interactive API documentation at:

```text
http://127.0.0.1:8000/docs
```

### 5. Start the SOC dashboard

In a second terminal, run:

```bash
streamlit run dashboard.py
```

The dashboard is configured to call the API at `http://127.0.0.1:8000`.

### 6. Evaluate model results

After the detection pipeline has generated the expected CSV file, run:

```bash
python evaluation_and_visualization.py
```

This script opens charts and prints classification metrics. It expects `../dataset/insider_activity_with_anomalies.csv` relative to the working directory.

### 7. Export the CSV to JSON (optional)

```bash
python csv_to_json.py
```

This reads the generated anomaly CSV and writes `../frontend/data.json`. Make sure the expected `frontend/` directory exists.

## API endpoints

The current `api.py` defines the following endpoints:

| Method | Endpoint | Purpose |
|---|---|---|
| `POST` | `/login` | Accepts a username and password and returns a JWT on successful authentication |
| `GET` | `/risk-data` | Returns risk-score records |
| `GET` | `/critical-threats` | Returns records classified as `Critical` |
| `GET` | `/alerts` | Returns alerts ordered by creation time |
| `GET` | `/user-info/{user_id}` | Returns profile information for a user |
| `GET` | `/user-files/{user_id}` | Returns recent file-access records where available |
| `GET` | `/user-logins/{user_id}` | Returns recent login records where available |

Except for `/login`, the API endpoints use bearer-token authentication. Consult `/docs` for the request parameters and response schemas exposed by the running application.

## Risk scoring

The detection script combines several model-derived signals into a risk score on a nominal 0–100 scale. Its current fusion weights are:

| Signal | Weight |
|---|---:|
| XGBoost probability score | 55% |
| Autoencoder reconstruction error | 25% |
| Isolation Forest score | 10% |
| Local Outlier Factor score | 5% |
| Absolute sensitive-file-access z-score | 5% |

The script labels scores using these thresholds:

- **Normal:** below 40
- **Review:** 40 to below 60
- **Critical:** 60 or higher

These settings are configurable in `anomaly_detection.py`; they are prototype rules, not universal security standards. Review the implementation and validate thresholds on representative data before operational use.

## Security notes

This repository is a development prototype and should not be deployed as-is in a production environment.

- The current `api.py` contains hard-coded demonstration usernames and passwords (`admin` and `analyst`). Replace this with secure user storage and password hashing before use beyond a local demo.
- Set a strong, private `SECRET_KEY` in `.env`. The API should fail safely if the key is missing; verify this behavior before deployment.
- Keep `.env`, database credentials, generated sensitive logs, and tokens out of version control.
- Use least-privilege database accounts rather than a MySQL root account.
- Add authorization checks so users with different roles can only access the records and actions they are permitted to use. The current token verification checks token validity but does not enforce role-specific permissions on each endpoint.
- Run behind HTTPS and configure production-grade error handling, logging, rate limiting, and secret management before deployment.
- Treat risk scores as investigation signals, not proof of malicious intent. Human review is important to reduce false positives and false negatives.

## Limitations

- Synthetic data is useful for testing code paths but cannot represent every real insider-threat scenario.
- Performance metrics can be misleading if the labels or synthetic data-generation rules are overly similar to the model's input features.
- Thresholds and scores require validation against realistic, representative activity logs.
- The project scripts use relative file paths and expect a pre-existing MySQL schema.
- Some API routes return an empty list if a query fails, which can conceal schema or database problems during development.
